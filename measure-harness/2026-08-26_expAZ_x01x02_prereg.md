# 사전등록 — 실험 AZ (X01/X02): `fe25519_mul` · `fe25519_sqr` M85 재스케줄

> 작성 2026-08-26, **측정 전**. 장부 ID **X01/X02**, 도구는 **T06(SLOTHY)**.
> 선행: expAY(X06 뒤 분모 확정), expAR/AS(단가·호출 수), AM1/AM1b(MVE 경로 기각).
>
> **【실행 후 보정 2026-08-26】** §2의 "곱셈 수가 하한"은 **가정이었고 expBA 로 실측 검증됐다**:
> M85 는 `umaal` 1개 + 스칼라 ALU 1개를 **같은 사이클에 발행**한다(페어링 100%),
> `umaal` 1.000 cyc, `adds` 0.500 cyc, 의존 체인과 독립 4-way 동일.
> **따라서 여지 34.2%/44.8% 는 실재한다.**
>
> 그러나 §3 의 방법(SLOTHY)은 프로젝트 자신의 확정 원칙과 충돌한다 —
> `slothy-2stream/README` §135: *"14레지스터를 꽉 채운 손 asm 은 스필 '추가' 없이는
> 어떤 스케줄러도 교차 불가"*. `fe25519_sqr`/`mul` 이 정확히 그런 코드다.
> **AZ-1(SLOTHY 직접 투입)은 실패가 예견되므로 착수하지 않는다.**
> 대안 경로 3가지는 `2026-08-26_expBA_results.md` §7 에 정리했으며 각각 새 사전등록이 필요하다.

## 1. 분모 — 실측 확정 (expAY)

X06 채택 뒤 `fe25519_mul` + `fe25519_sqr` 가 차지하는 비중:

| 연산 | total | mul+sqr | 비중 |
|---|---:|---:|---:|
| keygen | 639,278 | 95,900 | 15.0% |
| encaps | 1,012,208 | 371,319 | **36.7%** |
| decaps | 809,704 | 275,419 | **34.0%** |

주 표적은 **variable-base ladder 두 곳**(encaps `ssX`, decaps `ssX`)이다.

## 2. 이득 상한 — 곱셈기 직렬 하한 (정적 분석)

M85 는 곱셈기가 하나이고 `umaal` 체인은 **직렬 1/cyc** 다(로드맵 2026-08-17 실측:
SLOTHY 모델 v0.2 의 issue_rate=2 가 umaal 을 2/cyc 로 오판해 보드에서 30% 패배).
따라서 하한은 `명령수/2` 가 아니라 **곱셈 명령 수**다.

ELF 역어셈블에서 직접 센 값:

| | 총 명령 | 곱셈계(`umaal`/`umull`/`mul`) | 비곱셈 | 본문 실측* | **하한** | **여지** | 비곱셈/곱셈 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `fe25519_mul` | 120 | 73 (umaal 68 + umull 4 + mul 1) | 47 | ~111 | **73** | **34.2%** | 0.64 |
| `fe25519_sqr` | 94 | 53 (umaal 46 + umull 6 + mul 1) | 41 | ~96 | **53** | **44.8%** | 0.77 |

\* expAR 측정 창(115.005 / 100.006)에서 `bl`·복귀·`ldr` 2개 ≈4 cyc 를 뺀 값.

**비곱셈/곱셈 비가 둘 다 1 미만**이므로, M85 의 스칼라 슬롯에 비곱셈 명령을 전부
끼워 넣을 수 있다면 원리적으로 하한에 도달한다. **sqr 의 여지가 더 크다**(44.8%) —
M4→M85 이득이 sqr 만 −13% 였던 것(expAS §3.1)과 같은 방향이다.

### 2.1 상한 회계 (투영, 실측 아님)

하한에 완전히 도달한다는 **비현실적 가정**에서:

| 연산 | 절감 | X-Wing 대비 |
|---|---:|---:|
| keygen | 34,216 | −5.4% |
| encaps | 137,904 | −13.6% |
| decaps | 103,688 | −12.8% |

**이는 도달 불가능한 천장이다.** 절반만 회수해도 encaps/decaps −6~7% 다.

## 3. 방법 — SLOTHY (T06)

프로젝트에 이미 구축된 자산을 쓴다(WSL `~/slothy` + venv, 작업사본 `~/stitch2`,
`patch_slothy_v81m.py` v0.1~v0.4).

- **v0.3 패치 필수**: MAC 누산기 포워딩(umaal/umlal/umull → umaal/umlal 의 누산기
  in_out 의존만 latency 1, Rn/Rm 은 2). 이것 없이는 모델이 실리콘과 어긋난다.
- **issue_rate 는 2 로 두되 umaal 직렬성이 v0.3 으로 표현되는지 확인**한다.
  2026-08-17 의 30% 패배가 이 지점이었다.
- 입력은 `fe25519_sqr` 본문(94 명령) → 성공하면 `fe25519_mul`(120 명령).
  둘 다 분기 없는 직선 코드라 SLOTHY 의 전형적 대상이다.

### 3.1 순서

1. **AZ-1**: `fe25519_sqr` 를 SLOTHY 로 재스케줄. 모델 예측 cycle 기록.
2. **AZ-2**: 보드에서 micro 단가 A/B (expAM 슬롯 계보의 단독 벤치).
3. **AZ-3**: full X-Wing A/B (X06 on 상태에서 ABBA).
4. 성공하면 `fe25519_mul` 로 같은 절차 반복.

## 4. 사전 고정 kill gate

### 4.1 성능

- **AZ-2**: `fe25519_sqr` 단독 단가가 **5% 이상** 줄지 않으면 `fe25519_mul` 로 넘어가지
  않고 X01/X02 를 종료한다. (여지 44.8% 의 약 1/9. SLOTHY 가 이 정도도 못 찾으면
  모델이 실리콘과 맞지 않는 것이다.)
- **AZ-3**: full X-Wing 세 연산 중 **하나라도 회귀하면 채택 금지.**
- 모델 예측과 보드 실측의 괴리를 **반드시 기록한다.** 2026-08-17 처럼 모델이 이기고
  실리콘이 지면 그것이 결과다.

### 4.2 정확성 (전부 필수)

- `fe25519_sqr` 재스케줄본 대 원본: 무작위 1,000 입력 limb 단위 완전 일치
  (경계값 0, p−1, 2^255−1, all-ones 포함)
- RFC 7748 X25519 KAT 4종
- full X-Wing 8-seed 바이트 동일 + 암묵적 거부 동일
- 기존 전체 하네스 KAT·mismatch 0

### 4.3 상수시간

- 재스케줄은 명령 순서만 바꾸며 **분기·메모리 접근 패턴을 데이터 의존으로 만들지
   않는다**. 스칼라 all-zero/all-ones 분포 겹침 확인.

### 4.4 자원

- 명령 수·코드 크기 변화, ITCM working set, 레지스터 스필 발생 여부 보고.
- **스필이 생기면 그것이 곧 실패 신호다**(ldr/str 이 곱셈 슬롯을 잠식).

## 5. 위험

1. **SLOTHY 모델이 실리콘과 어긋날 수 있다.** 2026-08-17 에 이미 한 번 그랬고
   v0.3 으로 고쳤지만 `fe25519_sqr` 는 그때와 다른 커널이다.
2. **레지스터 압박**: `fe25519_sqr` 는 입출력이 r0–r7 이고 r8–r12+lr 만 스크래치다.
   SLOTHY 의 재할당 여지가 좁아 스필이 날 수 있다.
3. **ABI 계약 보존**: 입출력 r0–r7, sp 불변, `bx lr` 복귀를 반드시 유지해야 한다.
   `fe25519_sqr_many`·`fe25519_sqr_chain`·래더가 이 계약에 의존한다.
4. 코드가 커지면 ITCM 예산(현재 여유 약 22 KB)과 I-cache 거동이 바뀐다.

## 6. 바꾸지 않는 것
