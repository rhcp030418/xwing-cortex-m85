# 실험 BX 결과 — `vmov` core↔FP 발행 규칙, 그리고 **K14/K15 재정렬 접근 종료**

> 측정 2026-08-26. 보드 EK-RA8M1, DWT CYCCNT, REP_N=100, BATCH=64, 커널당 128 명령,
> `.balign 16`. 독립 flash/run 2회 동일.
> **expBR 의 전제가 틀렸음을 발견해 바로잡는다.**

---

## 1. expBR 은 틀린 전제 위에 서 있었다

expBR 은 `matacc_asm_*` 의 "MVE 28~38 명령"을 벡터 연산으로 보고 상한 32.4% 를 냈다.
매크로 전개 리스팅을 뽑아 보니 그것들은 **전부 `vmov s18, bufptr` 형태 — FP 레지스터를
스크래치로 쓰는 core↔FP 이동**이며 **MVE 벡터 산술이 하나도 없다.**

```
vmov s18,bufptr        <- MVE 가 아니라 FP 레지스터 스크래치
vmov s19,ctr
smulwt val0,ctr,bufptr <- 스칼라 DSP 곱셈
smlabb val0,val0,q,qa
```

따라서 상한이 **`vmov` 의 발행 비용**에 통째로 달려 있었고, 그 값은 **미측정**이었다.
이 실험이 그것을 잰다.

## 2. 측정 (128 명령/커널, 커널 간 차분)

| 커널 | 총 cyc |
|---|---:|
| A `umaal` × 128 | **247.08** |
| B `vmov s, r` × 128 | **247.20** |
| C `vmov r, s` × 128 | **247.08** |
| **D `umaal` 64 + `vmov s,r` 64** | **183.20** |
| **E `eor` 64 + `vmov s,r` 64** | **183.08** |

공통 오버헤드 X 를 A 에서 뽑는다(`umaal` = 1.000, expBA):

```
A : 128 x 1.000 + X = 247.08   ->  X = 119.08
B : 128 x r + X = 247.20       ->  r = 1.001   ->  vmov = **1.000 cyc/명령**
D : 작업량 = 183.20 - 119.08 = 64.12
      순차면 64 + 64 = 128 / 완전 페어링이면 64  ->  **실측 64.12 = 100% 페어링**
E : 작업량 = 64.00                                ->  ALU 와도 **100% 페어링**
```

### 2.1 확정된 규칙 (T18 에 추가)

| 명령 | 처리율 | 페어링 |
|---|---|---|
| **`vmov` core↔FP** (`vmov s,r` / `vmov r,s`) | **1/cyc** | **곱셈·ALU 와 100%** |

즉 `vmov` 는 **자기 포트에서 1/cyc 이지만 스칼라 포트를 막지 않는다.**

## 3. matacc 루프의 진짜 하한 — **9개 기본블록**

매크로 전개 리스팅에서 `matacc_asm_cache_16_32` 의 루프 몸통(113 명령)을 뽑아
**분기로 잘라** 기본블록을 셌다. rejection sampling 의 `bhs.w 2f` · `bne.w 2f` 때문에
직선 블록이 아니다.

| 블록 | 명령 | 곱셈 | store 워드 | `vmov` | 기타 | 하한 |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 8 | 0 | 0 | 0 | 8 | 4.0 |
| 1 | 4 | 0 | 1 | 0 | 3 | 2.5 |
| **2** | **37** | 10 | 6 | 8 | 13 | **22.5** |
| 3 | 2 | 0 | 0 | 0 | 2 | 1.0 |
| 4 | 4 | 0 | 1 | 0 | 3 | 2.5 |
| **5** | **38** | 10 | 6 | 7 | 15 | **23.5** |
| 6 | 2 | 0 | 0 | 0 | 2 | 1.0 |
| 7 | 10 | 0 | 0 | 7 | 3 | 7.0 |
| 8 | 8 | 0 | 0 | 6 | 2 | 6.0 |
| **합** | **113** | **20** | **14** | **28** | **51** | **70.0** |

하한 회계(expBA + expBL + §2.1): `곱셈 + store 워드 + 기타/2`, `vmov` 는 별도 포트.

```
실측 반복당 약 85 cyc  ->  여유 = (85 - 70)/85 = **17.6%**
```

**expBR 의 32.4% 는 과대평가였다.** 정정한다.

## 4. 판정 — K14/K15 의 **재정렬 접근**을 종료한다

### 4.1 조각화가 결정적이다

| 커널 | 스케줄 가능 블록 | 최대 블록 | 재정렬 실측 |
|---|---:|---:|---:|
| `fe25519_sqr` (expBB) | **1개** | 71 | **+14.80%** |
| `fe25519_mul` (expBD) | 3개 | — | +3.81% |
| `fe25519_mul` 평탄화 (expBM) | 1개 | 116 | +6.37% |
| **`matacc_asm_cache_16_32`** | **9개** | **38** | — |

expBD 가 확정한 규칙: **조각이 많을수록 회수가 급감한다.**
matacc 는 9조각이고 최대 블록이 38 명령이다. mul(3조각)보다 훨씬 나쁘다.

```
낙관적 추정: 여유 17.6% x (조각화 감쇠, mul 사례의 0.16 이하)  <  3%
연산당 = 50.6 kcyc x 3% = 1.5 kcyc
  keygen 0.24% / encaps 0.16% / decaps 0.19%   ->  평균 **0.20%**
```

**expBP §0 기준(1.0%) 미달 → K14/K15 의 재정렬 접근을 종료한다.**

### 4.2 남는 길과 그 성격

분기는 **rejection sampling 이 만드는 구조적인 것**이라 재정렬로 없앨 수 없다.
남는 길은 **제어 흐름 자체를 바꾸는 것**(예: 분기 없는 조건부 저장으로 rejection 처리)이며,
그것은 재정렬이 아니라 **알고리즘 재설계**다. 새 사전등록이 필요하고,
상수시간 성질(공개 seed 의존 변동)을 다시 논증해야 한다.

## 5. MVE 인지 스케줄러는 만들었으나 이 커널에는 쓸 데가 없었다

`measure-harness/expBB-src/resched_mve.py` — expBV(스칼라×MVE 100%)와 expBL, expBX 의
실측 규칙을 넣은 2-포트 스케줄러다. 그러나 **matacc 에는 MVE 벡터 산술이 없어**(§1)
이 커널에 적용할 이유가 사라졌다.

이 도구의 남은 표적은 **진짜 MVE 커널**(pqmx NTT/invNTT/basemul)과
**W03/W04/W05 의 2-stream 병합**이다. 후자는 **두 커널을 합치는 기능**이 더 필요하며
이 도구에는 아직 없다.

## 6. 미측정·한계

1. `vmov` **지연**(latency)은 재지 않았다. 처리율과 페어링만 쟀다.
2. §3 의 "반복당 85 cyc" 는 expBR §2 의 파생값이며 직접 계측이 아니다.
3. §4.1 의 "조각화 감쇠 0.16 이하"는 mul 사례 하나에서 온 **추정**이다.
4. `matacc_asm_opt_*` 3종은 같은 구조로 보이나 **블록 분해를 따로 하지 않았다.**
5. `resched_mve.py` 는 **어떤 커널에도 아직 적용해 보지 않았다** — baseline 재현 검증 미수행.
6. EK-RA8M1 한 개체, 이 배치 한정.

## 8. 정직 기록

1. **expBR 의 전제가 틀렸다.** "MVE 28~38"은 MVE 가 아니라 `vmov` core↔FP 였다.
   상한 32.4% → **17.6%** 로 정정한다. expBR 문서에 정정 주석을 단다.
2. expBR 이 "종료하지 않는다"고 한 판정도 이 문서가 **종료로 뒤집는다** — 다만
   이유는 상한이 아니라 **9개 기본블록 조각화**다.
3. §4.1 의 3% 는 **추정**이며 실측이 아니다. 융합 커널을 만들어 재지 않았다.
4. `resched_mve.py` 를 만들었지만 **이 실험에서 쓰지 못했다**(§5). 도구는 남긴다.
