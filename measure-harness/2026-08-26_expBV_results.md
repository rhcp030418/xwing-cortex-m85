# 실험 BV 결과 — M85 **스칼라 × MVE 동시 발행률 = 100%** (W03/W04/W05 분모)

> 측정 2026-08-26. 보드 EK-RA8M1, DWT CYCCNT, REP_N=100, BATCH=64, 커널당 128 명령,
> `.balign 16`. 독립 flash/run 2회 **비트 단위 동일**.
> 이 프로젝트의 본론(명령어 스티칭)이 성립하는지를 **처음으로 M85 에서 직접** 잰다.
> 기존 근거는 `slothy-2stream/README` 의 **합성 proxy 은닉률 61.7%** 뿐이었다.

## 1. 원시 측정 (커널 총 cyc/호출, 128 명령)

| 커널 | 총 cyc |
|---|---:|
| A `umaal` × 128 | **398.81** |
| B `vmul.i16 q` × 128 | **526.69** |
| C `vadd.i16 q` × 128 | **526.81** |
| **D `umaal` 64 + `vmul` 64 교대** | **398.69** |
| **E `umaal` 64 + `vadd` 64 교대** | **398.81** |
| F `umaal` 64 + `vldrw` 64 교대 | 2,320.69 |

> null 슬롯(160.69)은 쓰지 않는다. expBA·expBL 과 같은 이유로 **커널 간 차분**만 쓴다.

## 2. 해석 — **D = E = A**

**섞은 커널이 스칼라 단독 커널과 같은 시간에 끝난다.**
`umaal` 64개에 MVE 64개를 얹었는데 **한 사이클도 늘지 않았다.**

공통 오버헤드 X 를 A 에서 뽑는다(`umaal` = 1.000 cyc, expBA 실측):

```
A : 128 x 1.000 + X = 398.81     ->  X = 270.81
B : 128 x r_vmul + X = 526.69    ->  r_vmul = 2.000 cyc/명령   (MVE 2-beat)
C : 128 x r_vadd + X = 526.81    ->  r_vadd = 2.001 cyc/명령
D : 64 x 1 + 64 x 2 를 섞은 작업량 = 398.69 - 270.81 = 127.88 cyc
```

| | cyc |
|---|---:|
| 순차 실행이면 | 64×1 + 64×2 = **192** |
| 완전 겹침이면 | max(64×1, 64×2) = **128** |
| **실측** | **127.88** |

```
은닉률 = (192 - 127.88) / (192 - 128) = 100.2%   ->  **사실상 100%**
```

**M85 에서 스칼라 `umaal` 은 MVE 정수 연산 뒤에 완전히 숨는다.**
`vadd` 도 동일(E = A).

### 2.1 회수기 출력의 "32.1%"는 무시한다

회수기에 넣은 은닉률 계산식이 **null 슬롯을 뺀 값**을 쓰도록 돼 있어 32.1% 를 출력했다.
null 은 이 하네스에서 신뢰할 수 없다(expBA 는 IPC 3.34, expBL 은 3.2 라는 불가능한 값을
냈다). **§2 의 차분 해석이 정본이다.**

## 3. `vldrw` 는 예외 — 그러나 이번 측정은 **메모리 탓**이다

F = 2,320.69 로 크게 튄다. 작업량 = 2,049.88 / 64 ≈ **32 cyc per `vldrw`**.

**원인은 발행이 아니라 메모리 위치다.** 이 커널의 `scratch` 버퍼는 `.bss`(SRAM)이고,
expBJ §1 이 실측했듯 SRAM 적재는 DTCM 대비 약 6배 비싸다.
**따라서 F 는 "MVE 적재가 발행을 막는다"는 근거로 쓸 수 없다.** DTCM 기준 재측정이 필요하다
(§6-2 미측정).

> 참고로 `slothy-2stream/README` 는 스칼라×MVE 에서 `veor` 는 자유, `vstrw` 는 차단이라고
> 적었다. 이번 측정은 **연산(vmul/vadd)이 자유**임을 M85 에서 확인했고, **적재/저장은
> 확인하지 못했다.**

## 4. W03/W04/W05 의 상한 — 이제 분모가 있다

스티칭의 이득은 **ML-KEM 의 MVE 구간에 비어 있는 스칼라 슬롯**에 X25519 를 넣는 것이다.
§2 가 그 슬롯이 **실제로 비어 있고 공짜로 채워짐**을 보였다.

encaps 기준으로 MVE 가 지배하는 ML-KEM 커널(expAP §3.2):

| 커널 | cyc/연산 |
|---|---:|
| invNTT | 15,795 |
| NTT | 9,019 |
| basemul | 3,562 |
| **합 (거의 순수 MVE)** | **28,376** |

```
상한(이 세 커널만) = 28,376 / 977,896 = 2.90% of encaps
```

`matacc`(90,761)는 MVE 28~32 / 스칼라 85 로 **이미 내부에서 섞여 있어** 남는 슬롯이
적다(expBR §3). 그 몫은 **미측정**이다.

**→ 상한 ≥ 2.90%(encaps). expBP §0 기준(1.0%)을 넘으므로 W03/W04/W05 를 종료하지 않는다.**

## 5. 그러나 실행 수단이 없다 — expBR 과 같은 벽

스티칭을 실현하려면 **X25519 스칼라 커널과 MVE NTT 커널의 명령열을 하나로 엮어야** 한다.

1. `resched.py` 는 **재정렬만** 하고 두 커널을 합치지 못한다. MVE 도 모델링하지 않는다.
2. SLOTHY 는 이 프로젝트에서 **사용 불가 판정**됐다(`slothy-2stream/README` §135:
   레지스터 포화 손 asm 은 스필 삽입 없이 스케줄 불가). X25519 커널이 정확히 그것이다.
3. 손으로 엮으려면 X25519 래더 한 단계(약 2,020 cyc)와 NTT 층을 **레지스터 충돌 없이**
   교차해야 하는데, X25519 는 r0-r12+lr 을 모두 쓴다. MVE 는 q0-q7 을 쓰므로 **레지스터
   충돌 자체는 없다** — 이것이 이 방향의 유일한 희망이다.

**→ W03/W04/W05 는 "메커니즘 실측 확인 + 상한 확보, 수단 미확보"로 남긴다.**
이것이 이 프로젝트의 본론이며, 다음 단계는 **MVE 를 아는 2-stream 스케줄러**다.

## 6. 미측정·한계

1. **`vldrw`/`vstrw` 의 발행 성질 미측정**(§3). `.bss` 버퍼 탓에 이번 F 는 무효다.
2. `matacc` 안의 남는 스칼라 슬롯 **미측정**(§4).
3. §2 의 오버헤드 X = 270.81 은 "`umaal` = 1.000" 가정에서 나온 유도값이다.
   그러나 **D = E = A 라는 사실 자체는 그 가정과 무관하다.**
4. MVE 2-beat(2.000 cyc/명령)는 이번에 실측했지만 `vmul.i16`/`vadd.i16` 두 종뿐이다.
5. 실제 스티칭 구현은 **하지 않았다.** 이 문서는 메커니즘과 상한까지다.
6. EK-RA8M1 한 개체, 이 배치 한정.

## 8. 정직 기록

1. **회수기가 출력한 은닉률 32.1% 는 틀렸다**(null 슬롯 사용). §2 의 차분 해석이 정본이며
   그 값은 **100%** 다. 회수기 출력을 결과로 인용하지 않는다.
2. **커널 F 의 버퍼를 `.bss` 에 두었다** — expBJ §1 의 규율을 또 어겼다(expBM 에 이어 두 번째).
   그래서 F 는 무효로 처리하고 결론에 쓰지 않았다.
3. §4 의 상한 2.90% 는 "invNTT/NTT/basemul 이 거의 순수 MVE"라는 **가정**에 기댄다.
   그 세 커널의 스칼라/MVE 비를 따로 재지 않았다.
4. 이 문서는 **메커니즘이 성립함**을 보였을 뿐, 스티칭을 구현하지 않았다.
