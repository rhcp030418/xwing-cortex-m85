# 실험 BA 결과 — M85 스칼라×스칼라 듀얼이슈: **umaal + ALU 가 1 cyc 에 함께 발행된다**

> 측정 2026-08-26. 보드 EK-RA8M1, DWT CYCCNT, REP_N=100, BATCH=64, 독립 flash/run 2회.
> 목적: X01/X02(`fe25519_mul`·`sqr` 재스케줄)의 **이득 상한이 실재하는지** 확정.

---

## 1. 왜 필요했나

X01/X02의 여지를 "곱셈 명령 수가 하한"으로 잡으려면 **비곱셈 명령이 곱셈과 같은
사이클에 발행될 수 있어야** 한다. 프로젝트가 이미 잰 것은 **스칼라×MVE** 페어링뿐이고
(`slothy-2stream/README` 실험 N: veor 자유, vstrw 차단), **스칼라×스칼라**는 미측정이었다.

## 2. 커널 (각 128 명령, `gen/expBA_dualissue.S`)

| | 내용 | 겨냥 |
|---|---|---|
| A | `umaal r2,r3,r10,r11` × 128 (r2/r3 누산 왕복 = **의존 체인**) | 의존성 한계 |
| B | umaal 4-way 독립 (누산기 4쌍 round-robin) | 처리율 한계 |
| C | `umaal` + `adds` 교대 (독립) | **곱셈 × ALU 페어링** |
| D | `adds` 4-way 독립 | ALU 처리율 |

역어셈블로 각 커널이 정확히 140 명령(본문 128 + 프롤로그·에필로그 12)임을 확인했다.

## 3. 결과 — 두 run 완전 일치

| 커널 | 호출당 raw cycles |
|---|---:|
| A umaal 의존체인 | **167.16** |
| B umaal 독립 4-way | **167.19** |
| C umaal+adds 교대 | **103.19** |
| D adds 독립 4-way | **103.19** |

### 3.1 차분으로 단가를 뽑는다

공통 호출 오버헤드 `O` 는 차분에서 상쇄된다.

```
A − D = 63.97 cyc / 128 = 0.500 cyc   (umaal 1개 − adds 1개)
```

`adds` 가 2/cyc(0.5 cyc)라는 가설을 넣으면 `umaal` = **1.000 cyc**. 이 가설의 검증은
오버헤드가 두 경로에서 같게 나오는지다.

```
O = A − 128 × 1.000 = 39.19
O = D − 128 × 0.500 = 39.19      ← 완전 일치
```

**따라서 `adds` = 0.500 cyc (2/cycle), `umaal` = 1.000 cyc (1/cycle) 이 확정된다.**

### 3.2 세 가지 사실

1. **스칼라×스칼라 듀얼이슈가 존재한다.** `adds` 가 0.5 cyc/개 = **2 instr/cycle**.
2. **`umaal` 은 의존성이 아니라 처리율이 한계다.** 의존 체인(A)과 독립 4-way(B)가
   **167.16/167.19 로 동일**하다. 누산기 포워딩이 완전하다는 뜻이며, SLOTHY 패치 v0.3
   (MAC 누산기 in_out 의존만 latency 1)의 전제가 실측으로 재확인된다.
3. **`umaal` 과 ALU 연산이 같은 사이클에 함께 발행된다 — 페어링 달성률 100%.**

```
혼합 C (64 umaal + 64 adds):  실측 64.00 cyc
  직렬이라면        64×1.0 + 64×0.5 = 96.0
  완전 페어링이라면 64×1.0          = 64.0   ← 실측이 여기
```

**즉 M85 는 매 사이클 `umaal` 1개 + 스칼라 ALU 1개를 함께 발행한다.**

## 4. X01/X02 에 주는 결론 — 여지가 실재한다

곱셈 명령 수를 하한으로 잡는 회계가 **정당하다**.

| | 총 명령 | 곱셈계 | 비곱셈 | 본문 실측 | **하한** | **여지** | 비곱셈/곱셈 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `fe25519_mul` | 120 | 73 | 47 | ~111 | **73** | **34.2%** | 0.64 |
| `fe25519_sqr` | 94 | 53 | 41 | ~96 | **53** | **44.8%** | 0.77 |

비곱셈/곱셈 비가 둘 다 1 미만이므로 **모든 비곱셈 명령을 곱셈 슬롯 옆에 끼워 넣을 수
있다**(원리적으로). 현재 IPC 는 mul 1.08, sqr 0.98 로 **페어링이 거의 일어나지 않고 있다.**

### 4.1 스칼라 store 도 발행을 차단한다 — 하한 보정

커널 E~H 로 이어서 쟀다.

| 커널 | raw cyc | 판정 |
|---|---:|---|
| G `str` 단독 | 103.19 | **0.500 cyc/개 (2/cyc)** |
| H `ldr` 단독 | 103.19 | **0.500 cyc/개 (2/cyc)** |
| F umaal+`ldr` 교대 | 103.19 | 혼합 **64.0** = 완전페어링(**100%**) |
| E umaal+`str` 교대 | 167.19 | 혼합 **128.0** = **완전 직렬보다도 나쁨** |

- **`ldr` 은 umaal 과 자유롭게 페어링한다** (64 umaal + 64 ldr = 64 cyc).
- **`str` 은 umaal 과 전혀 페어링하지 못한다.** 단독 0.5 cyc 이던 store 가 umaal 과
  섞이면 **1.0 cyc** 로 올라가 총 128 cyc(= 64+64)가 된다. 직렬 예측 96 보다도 나쁘다.
  `slothy-2stream/README` 실험 N 이 MVE store 에서 관찰한 "스칼라 발행 완전 차단" 이
  **스칼라 store 에서도 성립**한다.

따라서 하한은 `곱셈 수 + store 워드 수` 다.

| | 명령 | 곱셈 | store 워드* | 본문 | **하한** | **여지** |
|---|---:|---:|---:|---:|---:|---:|
| `fe25519_mul` | 120 | 73 | 12 | ~111 | **85** | **23.4%** |
| `fe25519_sqr` | 94 | 53 | 14 | ~96 | **67** | **30.2%** |

\* `str` 5 + `strd` 1(2워드) + `push` 3(5워드) = 12 (mul);
`str` 3 + `strd` 1(2워드) + `stm` 1(8워드) + `push` 1 = 14 (sqr).
`stm`/`push` 의 실제 차단 폭은 워드 수로 **보수 가정**했으며 직접 측정하지 않았다.

**여지는 34.2/44.8% 에서 23.4/30.2% 로 줄지만 여전히 크다.**

## 5. 정직 기록 — null 슬롯을 쓰지 않았다

`expba_null`(프롤로그·에필로그만) 슬롯은 **64.78 cyc** 를 보고했는데, 차분에서 유도한
공통 오버헤드는 **39.19** 이다. 25.6 cyc 차이의 원인은 규명하지 않았다(스위치 dispatch
경로 차이나 I-cache 배치로 추정). **이 실험의 결론은 null 차감에 의존하지 않는다** —
§3.1 은 전부 커널 간 차분이고, 오버헤드는 A·D 두 경로에서 독립적으로 유도해 일치를
확인했다. null 슬롯 값은 보고만 하고 계산에 쓰지 않았다.

첫 판 회수기는 null 을 차감하는 방식이었고 그 결과 `adds` IPC 3.34 라는 **불가능한
값**(듀얼이슈 상한 2 초과)을 냈다. 그 판정은 어떤 문서에도 채택하지 않고 차분 방식으로
다시 짰다.

## 6. 한계

1. `adds`·`ldr`·`str` 을 시험했다. **`ldm`/`stm` 의 다중워드 차단 폭**, 시프트, 분기의
   페어링은 여전히 **미측정**이다 — §4.1 의 store 워드 수는 보수 가정이다.
2. 피연산자가 작은 상수(29×31)다. M85 곱셈기에 조기종료가 있다면 큰 피연산자에서
   달라질 수 있다 — 다만 `fe25519_*` 실측 IPC(1.08/0.98)와 이 결과가 정합하므로
   그럴 가능성은 낮다.
3. 커널이 128 명령으로 짧아 I-cache 에 완전히 상주한다. 큰 커널의 인출 대역은
   다를 수 있다.
4. EK-RA8M1 한 개체, 이 배치 한정.

## 7. 다음

X01/X02 의 **여지는 확정됐으나 도구가 막혀 있다.** `slothy-2stream/README` §135 의
확정 원칙:

> **14레지스터를 꽉 채운 손 asm 은 스필 '추가' 없이는 어떤 스케줄러도 교차 불가**
> (솔버는 재배치만 하지 스필 삽입은 못 함)

`fe25519_sqr`/`mul` 은 정확히 그런 코드다(r0–r7 입출력, r8–r12+lr 스크래치, 스택
누산기 사용). 따라서 SLOTHY 를 그대로 들이대는 AZ-1 은 **실패가 예견된다.**

가능한 경로는 셋이다. 어느 것도 아직 사전등록하지 않았다.

1. **손 재스케줄** — 페어링 100% 라는 사실을 알고 나면 사람이 umaal 사이에 캐리·adds 를
   끼워 넣는 것이 가능할 수 있다. 여지 34~45% 중 일부만 회수해도 크다.
2. **스필을 의도적으로 추가한 뒤 SLOTHY** — README 가 제시한 "C → `-ffixed` → 솔버"
   파이프라인. 단 AM1b 가 10×25.5 표현 경로를 이미 기각했으므로 8×32 를 유지해야 한다.
3. **곱셈 명령 수 자체를 줄이는 알고리즘 변경**(Karatsuba 등) — X09 계보이며
   별도 후보다.
