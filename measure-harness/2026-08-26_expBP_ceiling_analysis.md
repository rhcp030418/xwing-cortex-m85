# 분석 BP — 남은 가족들의 **상한 회계**와 종료 판정

> 2026-08-26. **새 보드 측정이 아니라 기존 실측치의 재계산**이다.
> 입력: expAP(ML-KEM 버킷), expAQ(XOF 배관), expAR/AS(X25519 세분),
> expBA/BL(발행 규칙), expBJ(Keccak 배관), expBN(현행 대표값).
> 새로 잰 것은 §4 의 `fe25519_add`/`sub` 재정렬 모델 하나뿐이다.

---

## 0. 판정 기준 (이 문서에서 미리 고정)

**상한이 "세 연산 평균 1.0% 미만"이면 그 가족을 종료한다.**

근거: 이 프로젝트가 이미 종료시킨 것들의 상한은 K19 4.6%(단일 커널), W11/W12 0.22~0.31%,
W16 25~32 cyc, K30 0.03% 다. 채택된 것들의 실현치는 X01 +1.16%(encaps), K31 +0.92~1.64%,
X02 +0.61~2.23%, X06 −10.83~−16.11% 다. **상한 1.0% 미만이면 실현치는 그 절반 이하**
(도구 실현율 0.37~0.70, expBD/BK/BN)이므로 투입 대비 회수가 맞지 않는다.

분모는 **현행 대표값**(expBN): keygen 621,106 / encaps 977,896 / decaps 785,540.

## 1. W10 — ML-KEM hash × combiner true 2-way Keccak: **종료**

W10 은 두 Keccak 을 2-way 로 겹쳐 **작은 쪽을 큰 쪽 안에 숨기는** 것이다.
따라서 상한은 **작은 쪽의 크기**를 넘을 수 없다.

| | cyc | 근거 |
|---|---:|---|
| X-Wing combiner (SHA3-256) | **2,537** | W11/W12 종료 회계 (장부) |
| encaps 중 비중 | **0.259%** | 2,537 / 977,896 |
| decaps 중 비중 | **0.323%** | 2,537 / 785,540 |
| keygen | **0** | combiner 없음 |
| **세 연산 평균 상한** | **0.194%** | |

**§0 기준(1.0%) 미달 → W10 종료.** 게다가 이는 "겹침이 100% 성공"을 가정한 상한이며,
2-way Keccak 은 lane 낭비가 있어(장부 K20 위험란) 실제로는 더 작다.

> W11/W12 가 이미 같은 이유로 닫혔다. W10 은 그 combiner 를 **다른 방법으로** 없애려는
> 시도였으나 분모가 같으므로 결론도 같다.

## 2. K29 — `rkprf` 조기 계산·병행: **표적 오류로 종료**

decaps 의 암묵적 거부 키는 `SHAKE256(z || ct)` 이며 입력이 32 + 1,088 = 1,120 B 다.
SHAKE256 rate 136 B → **9 블록 흡수 + 1 압출 = 약 9~10 permutation**.

| | cyc | 근거 |
|---|---:|---|
| permutation 단가 | **5,505.81** | expBJ §1 (DTCM) |
| `rkprf` 추정 | **약 50~55 k** | 9~10 × 5,506 (**추정** — 직접 계측 안 함) |
| decaps 중 | **6.4~7.0%** | |

분모는 크다. **그러나 K29 는 "조기 계산·병행"이지 "제거"가 아니다.**
FIPS 203 이 이 값을 상수시간으로 항상 계산하도록 요구하므로 **계산량은 1 cyc 도 줄지 않는다.**
겹치려면 **동시에 돌 다른 실행 유닛**이 있어야 하고, 그것은 W 계열(스칼라 × MVE 교차
스케줄)의 문제다.

**→ K29 를 독립 가족으로는 종료하고, 그 분모(50~55 kcyc)를 W04/W05 의 표적 목록으로 옮긴다.**

## 3. K07 — keygen `matacc→invNTT→noise→NTT` round-trip 재설계: **종료**

| | keygen cyc | 근거 |
|---|---:|---|
| invNTT | **11,882** (3 call) | expAP §3.1 |
| NTT 중 되돌리는 몫 | ≤ 9,038 (6 call 중 3) | expAP §3.1, **추정** |
| **round-trip 상한** | **≤ 20,920** | |
| keygen 중 | **≤ 3.37%** | 20,920 / 621,106 |
| **세 연산 평균** | **≤ 1.12%** | keygen 에만 적용 |

세 연산 평균 1.12% 는 §0 기준을 아슬아슬하게 넘는다. 그러나:

1. 상한 안의 NTT 몫 9,038 은 **추정**이며 실제로 되돌릴 수 있는지 미확인이다.
2. K07 은 **"noise 를 NTT domain 에서 더해도 되는 범위"의 수학적 증명**을 요구한다
   (장부 위험란). CBD noise 의 NTT 는 곱셈이 아니라 선형변환이므로 원리상 가능하지만,
   **FIPS 203 의 keygen 출력 바이트가 동일해야 한다**는 것이 이 프로젝트의 채택 조건이다.
   domain 을 바꾸면 `poly_tobytes` 대상이 달라져 **출력이 바뀔 위험**이 있다.
3. 실현율 0.37~0.70 을 적용하면 세 연산 평균 **0.4~0.8%** 다.

**→ §0 기준과 위험을 함께 보아 K07 을 종료한다.** 재도전은 "출력 바이트 동일"을 먼저
증명한 새 사전등록으로만 한다.

## 4. X03 — 독립 field op 를 `mul2`/`sqr2` 로 묶기: **종료하지 않는다 (상한 큼)**

**이 항목만은 §0 기준을 크게 넘는다.** 기록을 남긴다.

expBA 실측: `umaal` 은 **1.000 cyc, 처리율 한계**(의존성 한계가 아님).
따라서 두 독립 곱셈을 완벽히 교차해도 **곱셈 수의 합** 아래로는 못 내려간다.

| | 명령 | 곱셈 | 본문 실측 | 곱셈/본문 |
|---|---:|---:|---:|---:|
| `fe25519_mul_sched` | 120 | 73 | 약 **101** | 0.72 |
| `fe25519_sqr` (X02 채택본) | 94 | 53 | 약 **82** | 0.65 |

```
mul 2개 따로 :  101 x 2 = 202
mul 2개 융합 하한 :  73 x 2 = 146          -> 상한 절감 27.7%
sqr 2개 따로 :   82 x 2 = 164
sqr 2개 융합 하한 :  53 x 2 = 106          -> 상한 절감 35.4%
```

래더 한 단계에 **독립 쌍이 실제로 있다**:
`DA = D·A` 와 `CB = C·B`(독립 mul 2개), `AA = A²` 와 `BB = B²`(독립 sqr 2개).

encaps 기준 mul 26.1% + sqr 22.5% = **48.6%**. 그 중 쌍으로 묶이는 몫에 상한 27.7~35.4%
를 적용하면 **encaps 수 %p** 규모다. **남은 최대 표적이다.**

> **다만 미측정 위험이 크다**: 두 곱셈을 동시에 살리려면 레지스터가 모자라 스택 왕복이
> 늘고, `str` 은 발행을 차단한다(expBA). 추가 store/load 가 절감을 얼마나 먹는지가
> 이 후보의 성패이며 **아직 재지 않았다.** → 별도 사전등록 필요.

## 5. X05 — fused xDBLADD: **X03 에 흡수**

X05 의 "중간 store 지연·custom ABI"는 §4 의 융합을 구현하는 **방법**이다.
독립 가족으로 두면 같은 분모를 두 번 세게 된다. **X03 로 통합한다.**

`fe25519_add`/`sub` 자체의 재정렬 여지는 **없다**(이번에 측정):

| | 명령 | 모델 baseline | 실측 본문(expAS) | 재정렬 후 |
|---|---:|---:|---:|---:|
| `fe25519_add` | 23 | 28.0 | 약 26 | **28.0 (0.0%)** |
| `fe25519_sub` | 24 | 30.0 | 약 32 | 29.0 (3.3%) |

모델이 baseline 을 재현하고(28 vs 26, 30 vs 32) 재정렬 이득이 0.0~3.3% 다.
원인은 `umaal` 캐리 누산기 `r11` 의 **직렬 사슬**이며 순서를 바꿔도 풀리지 않는다.
**add/sub 단일 커널 재정렬은 종료한다.**

단, `add`+`sub` 를 **한 쌍으로 융합**하면(같은 피연산자를 두 번 `ldm` 하지 않고, 두
독립 캐리 사슬을 교차) 이야기가 다르다 — 그것은 §4 의 X03 와 같은 성격이며 그쪽으로 묶는다.

## 6. K28 — decaps 재암호화 compress+compare streaming: **종료**

| | decaps cyc | 근거 |
|---|---:|---|
| `verify`/`cmov` | **262** (1 call) | expAP §3.3 |
| `packing`(compress 포함) | **10,527** (9 call) | expAP §3.3 |
| **상한 (둘을 완전히 스트리밍해 중간 버퍼 제거)** | **≤ 10,789** | |
| decaps 중 | **≤ 1.37%** | |
| **세 연산 평균** | **≤ 0.46%** | decaps 에만 적용 |

**§0 기준 미달 → K28 종료.** 게다가 상한은 packing 을 **전부** 없애는 값인데,
compress 자체는 남아야 하므로 실제 여지는 그보다 훨씬 작다.

## 8. 이 문서로 바뀌는 것

**종료**: W10, K29(표적 오류), K07, K28, **X03/X05 중 "단일 커널 재정렬" 부분**.
**통합**: X05 → X03.
**유지**: X03(융합), K14/K15, K20/K21, W03/W04/W05, W14, E0.

## 9. 미측정·한계

1. §2 의 `rkprf` 50~55 kcyc 는 **permutation 수에서 나온 추정**이며 직접 계측하지 않았다.
2. §3 의 "NTT 중 되돌리는 몫 9,038"은 **추정**이다.
3. §4 의 융합 상한 27.7~35.4% 는 **추가 스택 왕복을 0 으로 놓은 낙관적 하한**이다.
   실제로는 `str` 발행 차단(expBA) 때문에 더 작다. **측정 전에는 절감률로 인용하지 않는다.**
4. expAP 의 버킷은 **계측 wrapper 가 붙은 빌드**에서 나온 것이라 절대 cycle 은 그 빌드
   한정이다(규칙 8). 여기서는 **비중과 상한 판정에만** 썼다.
5. §0 의 임계값 1.0% 는 이 문서에서 처음 고정한 것이며, 사후에 낮추지 않는다.
6. EK-RA8M1 한 개체, 이 배치 한정.
